# 第 03 课讲解稿

总时长八分钟：前三分钟讲用例图，接下来三分钟讲场景与非功能，最后两分钟回答提问。投影入口依次为故事 Issue、用例图、SRS 和追溯矩阵。

## 0:00～1:00：产品与用户

我们的项目是 AgentCloud，个人 AI 云端工作台。一句话是：给每个任务一个云端 AI 工位，回来接着做。

以课程项目为例，一个学生同时让助手修代码、整理实验数据和生成图表。他需要每个任务有自己的文件和环境，也希望去上课以后回来继续。我们的产品围绕多工位、保留工作现场和控制等待阶段的资源开销展开。

底层核心是高密度复用与成本感知调度。多个长期保留状态的任务按需要共享执行槽位；调度器判断等待时保持环境还是保存现场、让出资源。个人需求仍会通过学生和开发者访谈验证，已有系统与实验提供技术可行性依据。

## 1:00～3:00：用例图

请看用例图。左侧个人用户是主参与者，主要完成创建工位、提交任务、浏览文件、继续工位和查看用量。课程演示者与测试成员负责在独立环境进行策略对照和共享容量验证。

右侧是两个次参与者：推理服务返回模型结果，沙箱与快照服务提供工具执行环境和恢复能力。工作台、协调器和持久日志在 AgentCloud 系统范围内。

图中 17 个用例全部采用动宾名称。每个用例都能追溯到需求，例如“创建工位”对应 FR-06，“唤醒工位”对应 FR-08，“对照调度策略”对应 FR-04。我们准备了 24 条带负责人、证据链接和 Given/When/Then 的故事 Issue，其中七条覆盖质量要求，包含性能、安全和可用性。

用户任务会经历工作、等待模型、存档、休眠、唤醒和容量等待。界面状态根据后端确认记录展示，文件、操作回执和任务进度保持可查。

## 3:00～4:30：一条完整场景

重点看 UC-08“唤醒工位”。前置条件是工位已经休眠并保存了有效快照。用户继续任务后，系统登记返回需求，检查容量，再核验快照与执行身份。恢复成功后推进执行代次，打开工具入口，读取原来的标记文件，并展示实际恢复耗时。

这里有两类备选流。第一类是四个槽位都被占用：页面显示容量等待，沿用原操作身份继续查询，分别记录排队和恢复耗时。第二类是结果需要核对：页面展示原操作与允许的只读检查，保留恢复材料，按确认的流程处理。

验收时，我们会在真实 MEMORY 环境比较文件摘要、进程 nonce 和堆标记。本地 make demo 用 VOLUMES 验证文件恢复，演示中会标识实际恢复方式。

## 4:30～6:00：量化质量与技术价值

SRS 分成功能、非功能和约束三个部分。性能目标是：在写明的四核、16 GiB、20 会话测试环境中，1000 次列表或状态查询成功率至少 99%，P95 至多两秒，确认状态在五秒内呈现。模型生成、工具执行、排队和恢复各自报告实测耗时。

安全验收使用两个租户，对列表、详情、请求、文件和用量执行 20 次越权或无效凭据访问，要求全部被拒绝，并检查路径逃逸与浏览器产物里的测试服务凭据。可用性目标是在依赖和存储健康时，协调器重启三十秒内 ready，20 条已确认回执保持完整。

原项目已验证 64 个有状态 Agent 共享四个 gVisor 热槽位，形成 16× 会话复用，采用真实 MEMORY 与受控 CPU Mocker。正式 Gate 2 完成 50/50 trial、14,400/14,400 请求。我们会同时展示资源和交互等待的收益与代价，费用按实际用量及单价估算。

## 6:00～8:00：提问与材料定位

提问：为什么要保留原请求 ID？

答：页面刷新和重试都要找到同一任务。已确认操作沿原 ID 和输入查询持久回执，结果未知时保留原身份核对。

提问：16× 与个人使用费用如何关联？

答：16× 是会话数与热槽位数之比。个人费用根据计算资源、模型调用、存储和 I/O 的实际用量及单价估算，资源看板提供同负载基线。

提问：今天哪些已经实现？

答：已有后端、生命周期、工具回执、调度与实验工具。Web 工位、聊天和文件浏览、资源聚合是课程交付，进度和验收在每条故事 Issue 标明。

追溯矩阵把需求、用例、故事和证据连在一起。后续需求变更通过 Issue 与 PR；下次课使用已准备的类图、状态图和顺序图继续分析建模。
