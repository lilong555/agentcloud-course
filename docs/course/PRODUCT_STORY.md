# 产品故事

**AgentCloud 让更多有状态 AI Agent 共享有限的执行资源，并用成本感知调度控制复用过程中的资源消耗与交互延迟。**

## 谁需要这个产品

面向同时运行多个编程助手、研究助手或自动化任务的 Agent 平台开发者与运维人员。他们希望在固定的服务器预算下承载更多任务，并让任务在需要继续执行时及时获得资源。

## 为什么需要高密度复用

Agent 的执行过程具有交替性：调用工具时需要运行环境，等待模型回答或下一次交互时进入等待。每个任务又携带进程内存、文件、依赖和执行上下文，持续保留这些环境会占用热槽位与内存。随着会话数增加，等待中的 Agent 也在消耗平台容量。

以原项目验证的 64 个有状态 Agent 与 4 个 gVisor 热槽位为例，平台通过时间上的复用，让有限槽位轮流服务需要执行的 Agent。会话状态贯穿整个任务，热槽位按实际执行需求分配。这形成 16× 的会话 / 热槽位复用倍率。

## 调度算法如何创造价值

复用需要解决“什么时候释放、什么时候保留、什么时候恢复”的决策问题。释放过晚会延长资源闲置，切换过于频繁会积累快照、存储和恢复开销；少数任务长时间驻留又会增加其他任务的首次准入等待。

AgentCloud 从真实模型请求和闲置窗口估计剩余等待，测量快照、持久化与恢复耗时，并结合待恢复需求和 Worker 容量计算驻留成本。短等待或昂贵恢复可以选择 KEEP；释放收益覆盖切换成本时，在工具安全点保存 MEMORY 快照并 SUSPEND；返回需求到达且容量允许时 RESUME，继续原有任务。

现有 v2 策略基于条件剩余等待比较候选释放时刻的期望成本。样本不足时采用固定两秒期限，实际执行遵守安全点、最小驻留和稳定确认条件。持久回执、Actor 身份与 epoch 校验保障调度动作与正确的执行状态对应。

## 如何证明产品有效

在相同槽位预算、负载和随机种子下，对比固定 TTL 与成本感知策略，同时观察承载密度、总 Actor 预留 GB·s、请求完成率、有效吞吐和交互 TTFT P95。首次准入排队、恢复次数与耗时、快照数量及存储占用用于解释结果。

资源节省和交互延迟之间的取舍由实测结果呈现。原项目在高恢复成本负载中观察到驻留复用降低切换开销、首次准入等待增加，这为课程中的容量公平性与调度改进提供了明确问题。

## 课程交付

课程围绕高密度运行机制、调度策略分析与改进、统一实验协议以及可复现演示组织交付。调度诊断和图表帮助解释每次决策及其收益，界面用于展示实验和运行状态。

产品的一句话价值是：**在既定资源预算下，用可恢复状态与成本感知调度承载更多 AI Agent，改善资源利用并控制响应代价。**
