# 产品故事

**AgentCloud 是面向个人与高校学生的 AI 云端工作台：给每个任务一个独立工位，等待时保存现场、按需休眠，回来继续工作。** 高密度复用和成本感知调度为平价多开提供技术支撑。

## 从一个学生的日常出发

下面是用于需求访谈与原型设计的场景。小林正在准备课程项目：一个 AI 助手修接口，一个助手整理实验数据，另一个助手生成图表。三个任务拥有不同的文件、依赖和执行进度，他希望切换任务时各自都能接着做。

他手边是一台普通笔记本，多开运行环境会挤占内存；改用云端后，又需要关注等待期间的资源费用。如果环境在闲置后被回收，重新安装依赖、找回中间文件和恢复任务进度也会花时间。访谈将采集这些问题发生的实际频率、损失和现有应对方式。

小林期待的体验很简单：在浏览器里打开自己的几个 AI 工位，把任务交给助手；去上课后，回来还能看见原来的文件和进度，继续下一步。产品需要让他看清任务是否在工作、等待、休眠或唤醒，以及这几个工位用了多少资源。

## 谁会使用

| 用户 | 典型任务 | 最需要验证的价值 |
| --- | --- | --- |
| 大学生 | 课程项目、编程练习、数据处理 | 普通电脑管理多个任务，减少反复配置环境的时间 |
| 科研人员与研究生 | 分析脚本、实验整理、图表生成 | 保留文件和执行现场，分时继续多个工作区 |
| 个人开发者 | 同时排查不同问题、运行测试、维护小项目 | 独立工位减少任务干扰，控制等待阶段的云端开销 |

首轮从身边的学生、实验室同学和个人开发者招募。校园多人共享是后续容量验证场景，个人能否顺利开始、离开和继续任务是产品体验的核心。

## 希望交付的使用过程

1. **为任务开一个工位。** 用户创建“课程代码”“数据分析”“论文图表”等任务卡片，进入对应对话和文件工作区。
2. **把任务交给助手。** 助手调用模型和工具，用户能看见请求进度、工具结果和生成的文件。
3. **等待时智能休眠。** 系统根据等待长度和切换成本决定保留环境或存档休眠。工作中的工具先完成安全点流程，随后让出执行槽位。
4. **回来接着做。** 用户继续任务或模型结果到达后，系统登记执行需求，容量可用时恢复。工作台展示唤醒和排队状态，文件与运行现场按恢复记录核验。
5. **看见资源去了哪里。** 看板展示工位数量、执行槽位、资源用量与恢复耗时，帮助用户理解多开任务的代价。

这一过程借用了游戏机“休眠存档、唤醒继续”的直觉。AgentCloud 的调度器还要判断休眠是否划算：短等待或恢复代价高时可以保持环境，较长等待且释放收益覆盖切换成本时保存现场、释放槽位。

## 用户体验背后的技术

| 用户体验 | 技术支撑 | 验证方式 |
| --- | --- | --- |
| 平价多开，按任务保留工位 | 长期会话状态与短期热槽位分离，高密度时间复用 | 固定槽位数，测量完整请求完成情况与资源积分 |
| 存档后继续已有工作 | 工具安全点、MEMORY 快照、文件与进程状态校验 | 比较恢复前后的文件内容、进程标记和状态证据 |
| 休眠与响应兼顾 | 条件剩余等待估计、快照和恢复成本、容量压力 | 同负载比较资源、交互 TTFT P95、首次排队和恢复耗时 |
| 刷新后查回结果，重试复用原操作 | 持久请求、稳定操作 ID 和工具回执 | 同 ID、同输入读取原结果；未知结果展示查询与对账状态 |

现有 v2 在样本支持充分时比较条件期望成本，样本不足时采用等待阶段的固定两秒释放期限。持久回执、Actor 身份与 epoch 校验让生命周期动作与正确的执行状态对应。

## 课程 Web 工作台

**当前基础是后端、运行时、CLI 演示与实验工具；以下界面属于课程迭代目标。**

首页以多工位卡片展示任务名称、最近进度和状态。状态同时使用文字与图标，覆盖工作中、等待模型、存档中、已休眠、唤醒中、等待容量和需要处理的异常。排队与恢复时显示真实进度或已等待时间，恢复完成后展示记录到的耗时。

工位页面包含对话、工具结果和文件区。文件列表与浏览所需的聚合接口随前端接入补齐。演示时先生成一个带唯一内容的文件，经历挂起和恢复后再次读取，并展示内容校验结果；真实 MEMORY 演示同时核验进程状态。

资源看板展示会话总数、实际占用热槽位、休眠数、资源积分和恢复开销。节省比例取相同负载与窗口的基线资源积分，费用估算附价格与成本项。缺少采样的项目显示“待采集”。TTL 与 v2 的对照由独立演示运行产生，每次运行展示策略、配置、数据来源和完成情况。

## 如何证明它值得用

产品验证邀请学生与个人开发者完成“建工位—发起任务—离开—继续任务—找回文件”的操作，记录独立完成率、遇到的困难、可接受等待和预算。问卷与访谈用于确认多开需求、环境恢复成本和功能优先级。

技术验证保留高密度复用与调度算法的完整证据。原项目采用真实 Substrate MEMORY 与 Dynamo CPU Mocker，验证 64 个有状态 Agent 共享 4 个 gVisor 热槽位，复用倍率为 16×；Gate 2 在 N32 / N64、每规模五个种子、五种策略下完成 50/50 trial、14,400/14,400 请求。资源和时延随负载、策略与恢复成本一起报告，费用另按用量及单价估算。

课程演示先展示个人任务如何继续，再展示等待阶段如何释放槽位，最后给出 TTL 与成本感知策略的配对结果。后续校园共享实验记录实际参与人数与任务；已有 64 Agent 数据作为系统负载证据引用。
