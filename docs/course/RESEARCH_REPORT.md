# 需求调研报告

## 摘要与资料状态

AgentCloud 定位为面向大学生、科研人员和个人开发者的 AI 云端工作台。用户价值围绕多个任务独立进行、保留工作现场、离开后继续任务和减少等待阶段的资源开销展开；高密度复用与成本感知调度提供技术支撑。

当前调研依据为源码、接口、架构和历史实验报告。学生与个人开发者的访谈、问卷、原型试用处于计划阶段，下面的用户需求作为待验证假设；样本与结论随真实采集材料登记。执行安排见[调研计划](RESEARCH_PLAN.md)。

## 历史实验发现

原项目在单 Kind 节点、两个 Worker、四个 FIFO Actor permits、四租户及连续六轮任务的配置下，使用真实 Substrate MEMORY 和 Dynamo CPU Mocker 验证高密度运行。64 个有状态 Agent / 4 个热槽位形成 **16× 会话与热槽位复用倍率**。该倍率描述系统承载方式，个人费用由实际用量及计费价格估算。

正式 Gate 2 覆盖 N32 / N64、每规模五个留出种子、五种策略，完成 **50/50 trial、14,400/14,400 请求**。相对 TTL15 与 Observed，v2 在两种规模下达到资源与交互 P95 联合改善；相对 TTL2，N32 资源下降且 P95 区间跨零，N64 资源差区间跨零且 P95 更高。课程的策略演示需要同时呈现资源与等待，按具体基线解释结果。

现有 v2 通过已发生的模型请求、闲置窗口和历史观测估计剩余等待，以快照、持久化、恢复和日志耗时构成切换成本。样本充分时比较条件期望成本，样本不足时采用等待阶段固定两秒期限，实际动作遵守安全点与稳定确认。

高恢复成本负载显示：保留热环境可以减少快照和恢复次数，同时延长其他任务的首次准入等待。v2 的驻留成本已纳入登记的待恢复需求，规模 Runner 管理尚未登记返回需求的首次 FIFO 排队。将这类压力与驻留决策衔接，是改善新工位等待体验的候选研究问题。

## 资料调研结论

AgentCloud 已具有个人多工位所需的会话、工具、状态恢复与调度基础。课程重点是把这些能力接入可操作的 Web 工作台，并通过真实用户研究验证任务连续性、多开需求与预算偏好；技术工作持续围绕高密度复用和调度算法展开，用统一协议评价资源、交互等待与任务完成情况。
